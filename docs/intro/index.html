Why

Physical AI는 답이 흩어져 있는 도메인이다

어떤 업무를 개선할지, 기존 자동화·구매·SI가 충분한지 먼저 판단한다. 데이터·시뮬레이션·모델 학습은 필요한 경우에 선택하고, 성공·중단 조건을 합의한다.

01

역할별 시작

의사결정자는 업무·ROI, 기술팀은 실행·운영, AWS 직원은 발견 질문·지원 경계를 확인한다.

02

검증 범위를 구분한다

출시 상태·원문 대조·실험 재현·현장 검증은 별개다. 주장별 출처·확인일·검토 상태를 기록하며 자동 검사만으로 사실을 보증하지 않는다.

03

실험과 복구까지

고정 커밋 실행 경로 3개에 준비물·비용·평가·중단·정리 조건을 연결한다. 로봇 운영은 별도의 현장 승인과 복구 시험을 거친다.

What

5개 필러와 실행 가이드

기술 참조는 필러에서, 업무 적합성·ROI·실험·운영·근거는 목적별 페이지에서 확인한다. FAQ는 실제 문의 빈도 순위가 아닌 탐색용 예시다.

P1

데이터 수집 & 처리

로봇 학습의 병목은 모델이 아니라 데이터다 — 텔레옵 · 오픈 데이터셋 · 합성 데이터를 AWS 파이프라인으로 처리하는 법.

P2

모델 학습 (VLA)

VLA/로봇 파운데이션 모델을 어느 규모의 GPU로, 파인튜닝인지 사전학습인지부터 갈라서 설계하는 법.

P3

시뮬레이션

Isaac Sim/Lab vs 오픈소스 선택과 AWS 위에서의 대규모 병렬 시뮬레이션 실행 패턴.

P4

Sim-to-Real

시뮬레이션에서 학습한 정책을 실기체로 옮기는 검증된 방법론과 엣지 추론 배포 경로.

P5

에이전트 오케스트레이션

LLM 플래너(System 2)가 로봇 컨트롤러(System 1)와 플릿을 지휘하는 계층 — Bedrock AgentCore 중심.

Decisions

의사결정 트리 ×4

고객이 자주 부딪히는 4개 갈림길을 산문 대신 결정 표/트리로. 급하면 해당 표만 보고 방향을 잡는다.

Radar

대기열 / 관찰 목록

"이거 왜 없어요?"의 답. 포함 기준 미달로 대기 중인 항목이 한 줄로 존재하고, 기준 충족 시 본문으로 승격된다.

Maintenance

유지보수 규칙

소유권 · 갱신 규칙 · 승격 파이프라인. 새 후보 제보는 이 파이프라인을 통해 본문에 반영된다.

Decide

4개 갈림길, 표 하나로 판정

각 결정은 필러를 가로지른다. 트리와 비교표, 그리고 한 줄 판정 원칙까지.

Physical AI Playbook의 4개 교차 의사결정 트리와 각 핵심 질문, 판정 원칙
갈림길핵심 질문판정 원칙
Cloud vs Edge "이 추론을 클라우드에 둘 수 있나, 엣지에 둬야 하나?" 관측→동작 기한·지터·통신 단절 요구로 배치한다. 모델 내부 System 1/2가 클라우드 배치를 정하지 않는다.
NVIDIA vs 오픈소스 "Isaac에 다 걸까, 오픈소스로 갈까?" 워크로드로 고르면 된다. "AWS는 셋 다 잘 돌린다" — Isaac Sim/Lab · MuJoCo/MJX · Gazebo 모두 중립 포지션.
GPU 확보 전략 "On-Demand가 안 잡힌다. 뭘 써야 하나?" 시작은 On-Demand. 못 잡히거나 대규모면 Capacity Blocks / Flexible Training Plans로.
Build vs Buy "기존 방식·구매·SI·모델 적응 중 무엇이 적합한가?" 업무 성과·총비용·지원 책임을 비교한 뒤 선택한다. 오픈 모델은 코드·가중치·기반 모델·데이터 조건을 분리한다.
