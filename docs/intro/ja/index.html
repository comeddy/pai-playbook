Why

Physical AI は答えが散在するドメイン

Isaac Sim を AWS でどう動かすか、VLA ファインチューニングの GPU 規模は、sim-to-real gap は本当に克服できるのか — 答えは Slack スレッド、ベンダーブログ、論文に散らばっている。この playbook はその断片を検証基準でふるいにかけ、一箇所に階層化した。顧客ミーティングの5分前に開いても方向性がつかめるように。

01

5分で方向性

急ぎなら FAQ Top 20 へ直行、テーマが決まれば 5 つのピラーへ、岐路に立ったら意思決定ツリーへ。全項目は L0（1~2文）→ L1（1ページ）→ L2（deep-dive リンク）に階層化され、上部を読むだけで方向がつかめる。

02

検証済みだけを載せる

成熟度ラベル（GA / Preview / Research-only / Hype）と出典グレード [1]~[4] で全項目の信頼水準を明示。「印象的なデモ」と「デプロイ可能」を区別する。基準未達の項目は本文ではなく Radar キューにのみ存在する。

03

アクションで終わる

概念説明で終わる項目は未完成とみなす。全項目は「➡️ SA 次のアクション」で締めくくられ、読み終えれば顧客に何を提案するかが残る。

What

5つのピラー + 3つの運用ページ

ピラー間の比重は均等。各ピラー内は顧客の実需要 × production-readiness 順に整列し、上部には「顧客が最もよく聞く質問 Top 3」がある。

P1

データ収集と処理

ロボット学習のボトルネックはモデルではなくデータ — テレオペ・オープンデータセット・合成データを AWS パイプラインで処理する方法。

P2

モデル学習 (VLA)

VLA/ロボット基盤モデルをどの規模の GPU で、ファインチューニングか事前学習かをまず切り分けて設計する方法。

P3

シミュレーション

Isaac Sim/Lab とオープンソースの選択、AWS 上での大規模並列シミュレーション実行パターン。

P4

Sim-to-Real

シミュレーションで学習したポリシーを実機へ移す実証済みの方法論と、エッジ推論デプロイの経路。

P5

エージェントオーケストレーション

LLM プランナー（System 2）がロボットコントローラー（System 1）とフリートを指揮する層 — Bedrock AgentCore 中心。

Decisions

意思決定ツリー ×4

顧客が頻繁に突き当たる 4 つの岐路を、散文ではなく決定表/ツリーで。急ぎなら該当の表だけで方向が決まる。

「なぜこれが無いの？」への答え。基準未達の項目は 1 行で存在し、基準を満たせば本文へ昇格する。

Maintenance

所有権 · 更新ルール · 昇格パイプライン。新候補はこのパイプラインを通じてのみ本文に反映される。

Decide

4つの岐路を、表ひとつで判定

各決定はピラーを横断する。ツリーと比較表、そして一行の判定原則まで。

Physical AI Playbook の 4 つの横断的意思決定ツリーと、それぞれの核心質問・判定原則
岐路核心質問判定原則
Cloud vs Edge 「この推論はクラウドに置けるか、エッジに置くべきか？」 最重要の判別因子は制御周波数。リアルタイムの安全・反応ループならエッジ、考える時間があるならクラウド — action chunking が橋渡し。
NVIDIA vs オープンソース 「Isaac に全て賭けるか、オープンソースで行くか？」 ワークロードで選べばよい。「AWS は 3 つとも良く動かす」 — Isaac Sim/Lab · MuJoCo/MJX · Gazebo、いずれも中立ポジション。
GPU 確保戦略 「On-Demand が取れない。何を使うべきか？」 まずは On-Demand。取れない、または大規模なら Capacity Blocks / Flexible Training Plans へ。
Build vs Buy 「基盤モデルをファインチューニングするか、自前で学習するか？」 ほぼ常にファインチューニング（Buy+adapt）が答え。ゼロからの事前学習はごく少数 — 商用ではライセンスが最初のゲート。

※ インスタンス・リージョンの詳細は揮発性 — 判定前に playbook の最新リージョン表を確認。
